Newsletter and Project API Implementation Plan

Summary

Add custom PocketBase hook API routes for newsletter and project-management workflows while keeping the current database schema unchanged. Projects, tasks, subtasks, and milestones will continue to use the existing projects.gantt JSON field. Newsletters will continue to use the existing newsletters collection fields.

No schema migration is required for this plan. The implementation should only add server-side route handlers, validation, authorization, and frontend API wrappers.

Database Compatibility

  • Do not add, remove, or rename PocketBase collections.
  • Do not change existing field names or field types in projects or newsletters.
  • Keep tasks, subtasks, and milestones embedded in projects.gantt.tasks.
  • Represent subtasks using existing indentLevel.
  • Represent milestones using existing milestone: true.
  • Use existing statuses: pending, in-progress, completed, delayed.
  • Use existing newsletter statuses: draft and published.

Newsletter API Routes

  • GET /api/newsletters - list newsletters with optional status, page, perPage, and sort.
  • POST /api/newsletters - create a newsletter using existing newsletter fields.
  • GET /api/newsletters/:id - fetch one newsletter.
  • PATCH /api/newsletters/:id - update editable newsletter fields.
  • DELETE /api/newsletters/:id - delete a newsletter. Admin only.
  • POST /api/newsletters/:id/make-public - set status to published.
  • POST /api/newsletters/:id/make-draft - set status to draft.

Existing routes such as /api/newsletter/send-update, /api/newsletter/presentation-upload, /api/newsletter/subscribe, and /api/newsletter/unsubscribe should remain unchanged.

Project and Task API Routes

  • GET /api/projects - list projects visible to the authenticated user.
  • POST /api/projects - create a project with an empty normalized gantt object.
  • GET /api/projects/:projectId - fetch one project.
  • PATCH /api/projects/:projectId - update project metadata and visibility.
  • PATCH /api/projects/:projectId/status - update only project status.
  • GET /api/projects/:projectId/tasks - list project tasks from gantt.tasks.
  • POST /api/projects/:projectId/tasks - add a root task.
  • PATCH /api/projects/:projectId/tasks/:taskId - update a task or subtask.
  • PATCH /api/projects/:projectId/tasks/:taskId/status - update only task status.
  • DELETE /api/projects/:projectId/tasks/:taskId - delete a task and its descendant subtasks.
  • GET /api/projects/:projectId/tasks/:taskId/subtasks - list direct subtasks.
  • POST /api/projects/:projectId/tasks/:taskId/subtasks - add a subtask under a task.
  • GET /api/projects/:projectId/milestones - list milestone tasks.
  • POST /api/projects/:projectId/milestones - add a milestone task.

Implementation Approach

  • Add a new PocketBase hook helper module, for example pb_hooks/lib/api-manager.js.
  • Register the new routes from pb_hooks/main.pb.js.
  • Use existing PocketBase auth with $apis.requireAuth("users") for protected routes.
  • Mirror the existing frontend normalization rules for newsletters and Gantt data.
  • Patch only existing collection fields, mainly newsletters.status and projects.gantt.
  • Update frontend PocketBase wrapper functions to call the new routes where useful.

Authorization Rules

  • Newsletter create: author, manager, general_manager, or admin.
  • Newsletter edit: admin can edit all; other allowed roles can edit their own records.
  • Newsletter delete: admin only.
  • Project access: preserve current collection rule behavior: admin, general manager, creator, or allowed user.
  • Project/task mutation: same as project update permission.
  • Login: keep PocketBase built-in /api/collections/users/auth-with-password.

Validation Rules

  • Reject unknown statuses.
  • Normalize task dates, durations, progress, predecessor IDs, resource IDs, and milestone duration.
  • Prevent predecessor references to missing tasks.
  • When deleting a task, remove deleted task IDs from all remaining predecessorIds.
  • When creating a milestone, force milestone: true and durationDays: 0.
  • When creating a subtask, set indentLevel to parent indentLevel + 1.

Test Plan

  • Run npm run build.
  • Create, list, publish, draft, update, and delete newsletters.
  • Verify public users only see published newsletters.
  • Create, list, update, and status-change projects.
  • Add root tasks, subtasks, and milestones without changing schema.
  • Update task status through the status-only route.
  • Delete parent tasks and verify descendant subtasks are removed from gantt.tasks.
  • Verify existing manager UI still loads existing project and newsletter records.

Assumptions

  • make-darft means make-draft.
  • mailstone means milestone.
  • The API will be implemented as PocketBase hook routes, not a separate backend service.
  • The current database schema must remain backward compatible.
